# 源码移植与维护机制

## 输入和产物

[internal/port/rules.go](../internal/port/rules.go) 使用普通 Go 定义固定官方源码版本、抽取范围和 Context 改写规则，不使用外部配置文件。维护者提供包含该 commit 的本地 Go Git 仓库；工具读取 Git 对象，不要求或修改其工作树。默认离线、不自动更新 pin、不依赖该仓库当前 HEAD。

`cmd/syncgo` 已以 Go 实现 inspect、generate、check，并支持 M2 的多文件/整文件移植。运行方式和精确限制见 [M2 类型与状态记录](m2-universe.md)。本文件其余部分同时描述完整工具的后续目标。

- inspect：包/声明依赖、全局状态、环境访问、初始化顺序和符号映射报告。
- generate：在临时目录重建移植文件、验证后替换工具拥有的文件。
- check：重新生成并比较，检查 provenance、残留 internal import、全局状态和映射覆盖。

M1 inspect 使用 AST 枚举所有构建变体，记录词法引用和潜在副作用；不是别名分析。generate 对同包文件一起使用 go/types 做前后类型检查。WholeFile 保留类型、常量及已有 receiver；不自动去全局化。Context 已支持同包多文件的单名字状态声明，所有参与文件共享一个 Context 类型和构造函数；已支持具有显式 owner 的 receiver 方法。Declarations 可抽取真实 type、整组 const 和指定方法，OwnerRule 控制字段及分配改写；未知形式报错。

第一阶段仅针对固定 Go 1.27 源码，维护可审计规则。无需解决任意 Go 程序自动去全局化问题。

审计报告按需输出到 `_work/`，不参与 generate/check。正式目录只保留工具自动维护的 `sync/generated.json`，用于检查文件归属、来源与哈希，无需手工编辑。

## 路径映射

| 上游源路径前缀 | 项目内前缀 | 示例 |
| --- | --- | --- |
| `src/cmd/compile/` | 项目根 | `internal/ssa/func.go` |
| `src/cmd/internal/` | `internal/cmd/` | `internal/cmd/objabi/path.go` |
| `src/internal/` | `internal/go/` | `internal/go/abi/type.go` |

前缀后的目录、文件名和 package 名保持上游形式；移植文件不加 `upstream_` 前缀。规则只指定源文件，输出路径、来源包路径和 import 映射自动推导；package 名直接沿用解析得到的上游声明。provenance 中保留完整上游源路径，便于定位固定提交。

文件名中的平台后缀以及选中文件的构建约束也应保留。`_gen` 等子目录沿用相对位置，但生成器构建依赖、工具入口的移植仍需后续单独实现；路径映射不代表这些代码已能执行。`src/vendor/` 的依赖当前只进入 inspect，generate 尚未支持，后续明确依赖接入策略后再加入规则。

## 声明归属

Go 移植规则最终给每个选中声明指定一种处理方式：

| 方式 | 含义 |
| --- | --- |
| copy | 原样移植，仅 import/路径重定位 |
| transform | 按命名规则改写 receiver、状态引用、参数或初始化 |
| replace | 由明确的手写声明实现相同角色 |
| exclude | 不进入此库，记录理由及不存在未处理引用的证据 |

初始候选包清单不是最终生成规则。在 import 闭包上继续做声明可达性检查；同一包中 Build 不调用的函数仍可能造成编译依赖，必须拆出或提供真实适配，不能仅以运行时不可达忽略。

## 转换步骤

1. 验证精确源码 commit、VERSION 与 Go 1.27 约束。
2. 解析固定构建配置下的源码，收集符号身份和依赖。
3. 按 Go 规则选取声明，重定位 import，保存来源对应关系。
4. 将配置/状态读写改为 Context 字段访问；把包级初始化改为实例构造。
5. 对需要状态的函数传播 Context：使用已有 receiver、改为方法或补参数。
6. 改写调用点、函数值、闭包和回调装配；对接口实现和循环依赖单独验证。
7. 应用少量无法用常规规则表达的语义补丁。
8. 格式化、构建、静态审计及针对规则的正反向测试。
9. 产生每文件 source path/blob hash、规则 ID、工具版本、生成 hash 报告。

阶段 2 的符号解析不能依赖猜测的字符串替换。M1 使用 Go 1.27.1 标准库 importer，并按 Go 规则中包首次出现的顺序在内存中类型检查抽取的上游包，以原始 package path 提供给后续切片。未列入切片的 compiler/internal 导入明确拒绝，不读取宿主 GOROOT 私有包。完整前端依赖的解析在扩大切片时继续推进。

规则采用 package path + declaration + AST 结构定位。保留模式支持原有 receiver 和 method expression；对具有明确 owner 的 receiver 已能改写状态访问；这不等于任意方法都已去全局化。局部遮蔽按对象身份区分。

WholeFile 的 ZeroValues 只处理显式审阅的无初始化 struct 哨兵，将引用改为独立零值并删除全局声明；跨包消费者按解析后的对象身份自动沿用声明规则，保留 import 别名和局部遮蔽。初始化表达式变化、对哨兵赋值或残留包级变量会报错。

## 少量规则与大量生成差异

人工维护量的目标是少量规则类别与集中适配；移植结果的修改行数可能很大。升级报告分别统计：规则变化、手写适配变化、生成变化和残留特殊补丁。不能用生成 diff 很大来掩盖手工分叉，也不能为减少 diff 保留共享状态。

## 同包适配

每个移植包可以混合生成和手写文件：

```text
internal/ssagen/
  ssa.go                 移植生成：保持上游文件名
  intrinsics.go          移植生成：保持上游文件名
  adapter_context.go     手写：依赖和生命周期
  adapter_entry.go       手写：阶段入口和数据收集
```

同包手写文件以 `adapter_` 开头；工具对照固定上游检查文件名冲突。需要复用的适配设施可放独立包，通过显式导入连接。

生成器按文件所有权清单运行，仅删除上一轮由它生成且本轮不再需要的文件。不覆盖手写文件或被人工改动的生成文件；工具管理的包中不允许未登记的生产 Go 文件。先校验和暂存全部结果，普通 I/O 失败回滚，ledger 最后写入。多文件更新不保证进程被强制终止时的原子性；下一次 check 会发现中断造成的不一致。

## 上游生成代码

SSA 的 _gen、rewrite 规则和相关生成依赖必须与源提交一致。可先复制官方已生成文件再做确定性移植，但发布前要能验证这些文件与固定生成器/规则相符。上游生成步骤与本库重写步骤分别记录，禁止手工修补最终 rewrite 输出。

## 升级流程

在独立分支修改 `rules.go` 中的 pin → 重新 inspect → 审阅新增依赖/状态/操作 → 更新规则与适配 → generate/check → 状态隔离和语义差分 → 更新能力表与版本说明。

新字段、新 opcode、新 Aux 种类或新全局变量必须显式处理。不得静默丢弃未知操作或降低断言以获得测试通过。第一轮迁移演练在 Go 1.27.0 / 1.27.1 之间进行，不意味着同时对外支持两套实现。

每个移植文件保留上游版权头；首批源码的 LICENSE/PATENTS 已随生成器放入 `third_party/go/`，并记入 provenance。

## 已实现的跨文件状态转换

`pkg.go` 和 `type.go` 的 Context 规则共同描述 Universe 状态。工具在整个包的 go/types 对象上改写引用、函数值、递归和闭包，并沿用 Type/Pkg 的 owner；各文件的状态字段声明仍写在该文件对应的 Go 规则中。同包 Context 类型、构造函数或 adapter 不一致，以及重复状态/字段映射都会失败。

包级初始化遵循 go/types.InitOrder。工具将连续来自同一文件的初始化表达式放入原文件中的私有 receiver helper，由唯一构造函数按顺序调用，因此原文件 import 别名不会互相覆盖。显式 `ContextRule.Init` 才允许将源文件的全部顶层 init 转为实例方法；它们在变量初始化后按词法文件名和声明顺序运行，并保留各自 return/defer 的作用域。产物仍禁止包级 var 和 init。此能力不自动批准新依赖；新增 init 引用必须通过声明闭包、类型检查和环境依赖审计。

拥有状态的函数转为方法，`*Type` / `[]*Type` 等已登记 owner 类型参数在入口检查实例归属；不涉及实例状态或 owned 分配的原 receiver 方法保持原样。当前规则不推导任意容器、泛型、跨包状态参数和整个类型图的所有权，也不能替代后续对新增移植函数的 nil 语义审阅。

外部宿主函数通过 `CallRule` 显式绑定到 Context 方法，目前用于 base.Fatalf。源声明的函数签名从固定 Git blob 提取，只用于前置类型检查；后置检查要求 adapter 的完整签名一致，并审计最终产物没有残留宿主调用。工具不把源宿主函数体或签名壳输出到库中。跨包变量使用 `StateRule` 指定来源声明与 Context 字段，保持原类型，支持读写、取地址和闭包。只接受有显式类型的单变量声明，不复制宿主初始化表达式；宿主函数/状态源文件的哈希都计入生成记录。签名需要的同文件类型声明按依赖选取，其他包依赖仍须显式移植。

`ReadTables` 只处理显式登记、由常量整数构成的数组，将表声明放入每个使用它的函数。该规则用于上游 stringer 的索引表，支持索引读取及 len，写入或逃逸形式直接拒绝；不把其他全局状态视为只读表。

`Checks` 用于少量不能只靠直接 owner 参数判定的入口，例如 Field.Type/Sym 的归属和 Signature 的可空 receiver。规则只命名原声明和同包校验方法；工具自动按原参数顺序传参，在原函数体执行前校验，并要求 adapter 的参数签名与固定上游一致、无返回值。原算法不在 adapter 重写。该机制不自动识别所有嵌套对象或支持未审阅的 variadic/unnamed 参数。
